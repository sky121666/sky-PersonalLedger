# 自动修复执行提示词与规范

本文件是本次任务的执行合同，不修改机器或其他项目的全局规则。

## 可复用提示词

> 在已授权项目内，先核验当前代码、工作区和发布对象，将有证据的问题转为业务不变性和验收示例。给出具体修复设计后持续实现、测试、独立审查和交付。每项修复先写能在旧代码失败的回归，再解决根因；保留兼容数据、已完成副作用和用户最新状态。主动寻找反证并自我批判，不用测试数量、代码数量或“全绿”冒充可靠性。按功能与风险拆分提交，使用既有受保护 PR 和不可变版本发布流程，逐层验证源码、产物身份、公开下载和实际运行。不要修改真实业务数据，不泄露凭据，不绕过保护，不覆盖历史版本。失败后定位原因，写入超时先核实状态；持续推进到当前验收条件全部满足，仅在必要授权或外部条件确实缺失时暂停受影响动作。准确报告已实现、实际验证、公开发布与剩余外部验收。

## 执行规范

- CAL 固定记录 Goal、Constraints、Acceptance Criteria、Ambiguities、Skill；有效授权与校准复用。
- 一项根因对应可观察的 RED→GREEN；覆盖成功、空值、部分失败、乱序、并发和重启。
- 所有模型/API/备份字段变化检查直接调用方与旧数据；数据库模型不直接决定备份合同。
- 只修改拥有的路径，发现并发修改先比较；分组提交由协调者顺序执行。
- 提交与发布树单独检查：派生配置、依赖目录及其符号链接不能当作源码。发现尚未推送的意外文件时保留恢复分支，从干净基线生成只含确认源码的交付分支。
- 数据库和运行诊断只用独立合成实例；凭据通过现有安全配置读取，不进入普通证据。
- 每项完成前自问：证明了业务目标还是仅证明了当前实现？是否新引入兼容性或安全退化？
- 在功能验证之外设置独立反证审查；测试失败不能删断言、放宽权限或跳过关键路径。
- 发布证明单独检查签名真实性与执行来源：证书实际调用工作流、可信触发 ref、来源/签名提交和产品身份须分别匹配；同仓库普通分支的有效签名不能替代受保护发布 job。
- 证据记录版本、源码/内容指纹、命令、退出码、范围、结果与开放边界；历史记录不冒充当前证据。
- 按既有门禁合并和发布，不修改远端保护来换取自动化；环境批准使用已获授权的正常路径。
- 不可变 tag、镜像和资产创建一次；未知结果先读取，确认未发生后才考虑安全重试。
- 来源反例成立后停止受影响候选推广并保留原 tag；使用新版本与新源码修复，不能覆盖旧 tag 或重跑不含修复的旧发布源码。v1.0.10 的停止记录与 v1.0.11 新候选分别保留。
- 达到验收即停止，不追加无关重构、功能、依赖或规则系统。

## 批判性复核模板

每项重要结论必须回答以下问题，并将确定反例交回修复流程：

1. **事实与假设**：哪些结论来自代码、实际运行或文档？哪些只是推断？证据能否支持所声称的范围？
2. **最强反例**：如果响应乱序、用户反悔、辅助查询失败、进程重启、旧数据恢复或干净 CI 检出，结论是否仍成立？
3. **修复的代价**：是否破坏旧客户端、备份读取、默认禁用状态、认证撤销或发布恢复？是否只是把错误移到另一个层面？
4. **验证的独立性**：测试是否只复述实现？Mock 是否遮住浏览器 Cookie、真实数据库、文件选择器或发布权限？有效签名是否实际来自可信调用 ref，还是普通同仓库分支也能伪造谓词？证书中的调用 URI/ref 和来源提交是否与产品/工具身份各自匹配？
5. **自我纠正**：发现反例后明确撤回原来的过度结论，保留失败证据，调整设计和回归测试，再交给独立复审。

评审报告逐项覆盖业务逻辑、架构、落地、优缺点、七类风险、六维评分、具体整改和最终判断。缺少商业需求证据时标明待验证，不把源码正常运行等同于需求真实；修复后的分数须依新证据重评。

此前 v1.0.10 候选的业务测试与签名结构测试未覆盖可信调用 ref 反例。新增反例推翻了“有效签名即可证明受保护扫描已执行”的结论；原评分保留其评审时间和判断性质，不因测试数量增加而自动提高，也不充当发布统计证据。v1.0.11 的来源合同见 [发布治理合同](release-governance.md)；正式发布状态须核对对应 Release 页面、当次运行记录和公开资产。
