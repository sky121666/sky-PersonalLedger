# 项目复评与修复核对 · 2026-10-06

本评审对象为 PersonalLedger 的个人/家庭私有记账、Go API、Vue Web、Flutter 客户端和现有 Docker/Web 发布链。依据当前代码、合成数据测试及独立反例审查；不把历史截图、模拟器或测试数量视为生产、签名分发或市场需求证明。

## 一、整体逻辑

收支、转账、余额、提醒、借贷、预算、家庭维度、备份与导出构成合理业务闭环。已修复删除记录恢复后复活、归属和付款人混用、成功写入被辅助刷新误报失败等断层。家庭成员目前是账务维度，不能推断为独立登录角色。

私有保存和家庭归属属于明确的问题域；未提供用户访谈、留存或付费数据，因此不能据代码断言市场需求强弱。软件能运行与商业需求成立须分别验证。

## 二、整体架构

保留单体 Go API、共享关系数据库和两类客户端，符合当前单实例体量。事务、固定账户锁顺序、一致性读快照、附件维护屏障及独立凭据加密是有效基础。专用备份 DTO、认证会话身份、异步代次和原子设置合并补上此前契约缺口。

仍有较大页面和两端手写契约，维护与行为一致性成本偏高。后续按功能边界逐步拆页面、统一契约和错误语义即可；没有证据支持为当前规模引入微服务或全局重写。共享上传根目录的多实例写入、离线同步、多租户不在已支持架构内。

## 三、可行性与落地

技术路径可落地：SQLite 私有部署为主，PostgreSQL/MySQL 有实际隔离矩阵；Docker/Web 走受保护 PR、不可变 tag、两架构扫描和 digest 固定产物。上线对象、真实业务数据与移动签名材料未提供，不能假称已在用户生产环境安装。

未给出团队人数、交付预算和持续运维资源，不能给出可信的人天/成本承诺。当前主要卡点由代码可靠性转向真实环境配置、备份持有、升级验收和跨平台签名分发。优先维持单可写实例与现有门禁，不以未验证的大重构增加交付依赖。

## 四、优缺点

优势：资金写入事务化；认证、凭据与隐私边界明确；备份包含历史与附件；双客户端覆盖完整；发布源码、扫描和产物有可追溯身份。

缺点：客户端合同重复、页面体积大；部分业务状态依赖网络；单进程协调限制扩展；缺少市场验证和明确 LICENSE；真实设备系统保存及签名分发没有自动单元测试可替代的证据。

## 五、风险与处置

| 类别 | 实际风险 | 处置或剩余边界 |
|---|---|---|
| 技术 | 删除/禁用状态丢失、读取不同时间的余额与账单 | 2.4 专用 codec、一致性快照、真实恢复不变性 |
| 业务 | 归属与付款人混用、已记账后重复操作 | 两字段独立、提交结果与读取失败分开 |
| 逻辑 | 迟到响应覆盖当前表单、日期、月份或会话 | 固定身份/代次、加载时冻结输入、认证响应顺序 |
| 运营 | 历史演练或过期日志冒充当前可信证明 | 当次 HTTP JSON、当前 SHA/指纹、受保护签名证明 |
| 安全 | 凭据外泄、错误吊销新登录、计划关闭被旧任务覆盖 | 凭据排除、精确刷新会话撤销、字段原子合并与发送前复核 |
| 迭代 | 两端规则分化、旧读取器不能读取 2.4 | 两端回归、版本合同、旧格式读取与升级前一致性副本回滚 |
| 落地 | 生产对象/签名/设备缺失 | 自动交付以 Docker/Web 为范围，外部验收单独列明 |

容器升级/回滚实际核验了 schema 10→11→10、余额与附件/删除状态恢复。停止命令成功但进程退出码 2，代码没有 HTTP 请求排空实现；本次只能证明停止写入后的副本恢复路径，不能称不停写无损热升级。

## 七、具体整改与反证

| 已确认问题 | 最小整改 | 业务验收 |
|---|---|---|
| 软删除、禁用状态恢复变化 | 专用 2.4 DTO；事务内保存明确 false/zero | 删除仍删除、余额/支出/状态不变 |
| 部分 JSON 清空账本 | 版本要求必需集合，区分缺失与明确空 | 返回 400、已有账本不变 |
| Web 编辑 A/B 交错或加载覆盖输入 | 固定保存 ID、代次、冻结加载输入 | 最终 PUT 对象/值均来自当前已加载编辑 |
| 普通备注编辑覆盖付款人 | 两端独立字段与选择器 | A 归属/B 付款编辑后保留 |
| 前端退出、refresh 和新 login 交错 | 会话代次与完整认证请求排队 | 旧响应不复活/清新会话 |
| 过期 Access 无法撤销 Cookie 会话 | 同源/CSRF 和签名刷新身份撤销 family | 旧 refresh 无法 bootstrap，新独立登录保留 |
| 改密迟到响应删除新 Cookie | 服务端撤销保持，改密响应不写 Cookie | 真实 CookieJar 保留新登录并可刷新 |
| 首页可选失败隐藏资产、换月旧数 | 独立结果与成功查询身份 | 未知显示未知，失效读取静默，实际失败可重试 |
| Flutter 恢复后旧页面/返回遗漏刷新 | session/data 绑定的持久完成回调与路由重建 | 页面退出后恢复仍刷新，旧会话回调失效 |
| 模板写入后列表失败导致重复记账 | 写成功先刷新，失败只重试读取 | 不再重复 apply |
| 导出文件没有取走入口 | 原生系统保存、Web Blob 下载与准确状态 | 字节/文件名正确；取消/失败不称成功 |
| AI 计划完成覆盖关闭开关 | 原子合并运行记录，发送前读最新配置 | 用户关闭持续生效 |
| 四种 AI 任务相同、错误内容缓存 | 类型 prompt、严格类型/规范键/非空 summary | null、错误大小写别名不 completed/cache |
| AI 调用无明确约束 | 每用户并发 2/每分钟尝试 6/输出 4096 | 缓存不耗额度，超额不发外部请求 |
| clean CI 清单空集、旧演练放行 | 基线差异精确清单、实际 HTTP proof | 未登记提交/错误 SHA/指纹/时间拒绝 |
| 恢复依赖短期 Actions 日志 | OIDC 签名绑定源码、策略、run、digest | v1.0.10 起签名失效不降级 |

自我批判实际改变了实现：初始前端 generation 不能控制 Cookie；Go 的 null 与大小写不敏感解码产生校验差异；页面退出漏失效；真实浏览器暴露了 mock 未覆盖的加载输入竞态。各项都保留 RED→GREEN，再经独立复审。新增扫描证明测试接入 CI，避免仅本地验证。

## 八、明确结论

整改后整体判定为**良好**，以个人/家庭单实例私有部署为定位，可以按既有部署与升级规程落地。当前采取关键链路修复和局部结构调整，无须彻底重构。后续合同整理与页面拆分属于渐进优化，不阻塞已经验收的交付范围。

在最后发布门禁通过前不能称已发布；Docker/Web 产物的公开运行不等于已部署用户服务器，更不等于签名移动安装、实体设备或商业运营验收。具体源码、CI、digest 与资产身份在最终交付中列明。
